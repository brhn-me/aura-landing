0.13.0-rc.2

2026-10-18Pre-release

Second pre-release of 1.3.0 (internal, not published): the fixes from the owner's rc.1 review (#293 – #308) and the one the rc.2 emulator pass found (#299's press circle). Also: Docker Compose installs are always the project aura now, whatever the folder is called: an existing compose install keeps its library only with COMPOSE_PROJECT_NAME=avp in .env or after copying the volume once (docs/ops/upgrade.md). The project's links point to github.com/brhn-me/aura.

Show all changes

Changed

  • The Info dialog no longer has "Copy link at 1:23"; links that start at a time still open there (#294).
  • The sidebar's Admin is now called Administration, also in the More sheet and the Android drawer (#296).
  • The Light theme is no longer marked "(Beta)" (#297).
  • Favorites no longer lists a Downloads tab where downloads aren't available, and its address opens Favorites there (#295).
  • Rating stars are gold instead of the accent red everywhere, and smaller in Now Playing (#306).
  • Android: the playing bars over the artwork are back in the accent red, and the play area's thumbnail shows 5 thicker bars instead of many thin ones (#298).
  • Docker Compose: the project is always aura (container aura, volume aura_aura-data), whatever the checkout's folder is called; make up tries a build in its own aura-dev project, so it never upgrades or deletes an install's library. Existing compose installs keep their library in <folder>_aura-data (usually avp_aura-data): set COMPOSE_PROJECT_NAME=avp in .env, or copy the volume once (docs/ops/upgrade.md) (#307).
  • The server logs one clear line when it upgrades a library from an older version: "upgrading the library from X to Y, backup at …" (#307).
  • The project's links point to github.com/brhn-me/aura.

Fixed

  • Android: the bottom bar's highlight is a circle behind the icon instead of a wide shape, and a tap no longer leaves it on; the same on phone browsers (#299).
  • Android: the video view has a Devices button, so a playing video can be moved to another device (#302).
  • Thumbnails and cards are sharper on high-density screens: artwork is requested for the screen's pixel density (smaller with Data Saver) (#303).
  • The Now Playing view's Up Next has the same rows as the queue: the drag handle left of the thumbnail, the ♥ beside the remove button; a queue of songs only has no empty space after the artwork; the floating queue is wider, and its Now Playing row's title uses the whole width (#293).
  • Android: the full queue has the drag handle left of the thumbnail (in the queue drawer it shows while a row is dragged), and both end each row with the length, then the ♥; no remove button (swipe or the row's menu removes); the full queue's header actions are in a ⋯ menu; the swipe-to-remove area is a calmer red (#293).
  • The ♥ at the end of a station row (Browse Stations), Most Played and Recent no longer sits far in from the row's edge (#300).
  • A playlist's ⋯ is right after Download again, its track list has no clock in the header, and its ♥ column lines up with the other lists' right edge (#304).
  • A playlist's ⋯ → Sort by no longer shows the current order beside it (it is checked in the submenu), which broke the menu on phones; the other hints shorten instead of pushing the arrow out (#305).
  • A download site's watermark in a song's lyrics tag (such as music.com.bd), a web address, an e-mail or text without letters no longer counts as lyrics: no Lyrics button, and real lyrics are shown without such a line at the start or end. Existing libraries need no rescan; the Metadata editor still shows the tag (#301).

Docs

  • Backups with Docker are inside the data volume: how to copy them out, and an optional host folder for them in docker-compose.yml (#308).

0.13.0-rc.1

2026-10-16Pre-release

First published pre-release of 1.3.0. 1.2.0 was never released past 1.2.0-beta.1: its work ships here too. New in 1.3: offline use: the apps keep the library on the device and open as usual when the server can't be reached (pages, small covers and search from what is kept; songs that can't play here are dimmed and can be saved for later; Favorites and recent music kept by themselves in the Android app; favorites, ratings and plays made offline are sent once the server is back), and the Android and desktop apps keep that library in their own database. Also Download on a song's or video's own page, Copy link at the current time, the sleep timer in the web video view, "Tap to play here" for a tab that was never clicked, and a closed video view plays on as sound alone. Details per step in the 1.3.0-alpha sections below. Since alpha.4: the real-phone checks (B-33) and the fix they found (#291), below. Upgrading from 1.2: the server's default port is 7780 now; with Docker change -p 3000:3000 to -p 7780:7780 (or keep PORT=3000). The database upgrades itself and writes a backup first.

Show all changes

Changed

  • In the Android app, the library kept for offline use is now in the app's own database instead of its web view: it takes much less memory with a large library (about 31 MB less with 50,000 tracks) and Android doesn't clear it with the web view's data; the first start after the update fetches it again (B-64).
  • The desktop app keeps the library for offline use in its own database too: much less memory in the window with a large library (about 24 MB less with 50,000 tracks) (B-64).

Fixed

  • A download started just before leaving the page could stay "Queued" forever; the album, playlist or song and its tracks are now saved together (#289).
  • Android: pressing Play on the lock screen (or the notification, or a headset) after another device took over made both devices play while the phone stayed locked; the phone now takes playback back and the other device pauses (#291).

0.13.0-alpha.2

2026-10-14Pre-release

Second internal pre-release of 1.3.0 (not published): offline use. The app keeps the library on the device and opens as usual when the server can't be reached: its pages, small covers and search come from what is kept, songs that can't play here are dimmed, a tap on one offers to save it for later, Favorites and recent music are kept by themselves (on in the Android app), and favorites, ratings and plays made offline are sent once the server is back. Also: a swiped-away picture-in-picture window plays on as audio only.

Show all changes

Added

  • Offline library (B-08, B-10): the app keeps the library's list and small covers on the device and refreshes them while the server is there. When it can't be reached, the app still opens on its usual start page, the library pages (albums, artists, genres, playlists, Favorites, Recently and Most Played, search) show from what is kept, songs that can't play on this device are dimmed, pages only the server has say "Needs the server", and one short notice says so (Settings → Playback → Offline Notice turns it off). Settings → Playback shows how many tracks are kept. Web, desktop and the Android app.
  • Keep Music Automatically (B-09, Settings → Playback): the device keeps your Favorites, the last 50 Recently Played and the top 50 Most Played songs by itself, up to a size limit (1, 2, 5 or 10 GB; 2 GB by default), on Wi-Fi unless Download on Mobile Data is on. On by default in the Android app, off on the web and desktop. Songs still in the song cache also play offline.
  • Save it when the server is back (B-11): offline, tapping a song that isn't on the device asks to save it; it downloads once the server can be reached again. A queue started offline skips what isn't on the device.
  • Changes made offline are sent later (B-12): favorites, saved albums, ratings and plays made while the server can't be reached are kept on the device and sent when it is back (the last change wins); plays keep the time they were played.
  • Swiping the picture-in-picture window away in the Android app keeps the video playing as audio only, without downloading the picture (B-36).
  • Server: GET /api/v1/library/snapshot, the whole library for a device in one request (ETag, 304).

Changed

  • A download that fails because the network or the server is away stays queued and goes on by itself once they are back (it used to fail and need Retry) (B-11).

  • Android app with Read Ahead on: each song is downloaded once again (the next song was fetched twice: once by the player preparing it, once past the cache by the read-ahead) (#181).

0.12.0-beta.1

2026-10-11Pre-release

Second pre-release of 1.2.0, internal (not published), and the start of release/1.2: from here only fixes for the owner's beta testing go into 1.2. New since alpha.1: internet radio Browse stations, video downloads and native picture-in-picture in the Android app, low-memory handling, the shuffle order fix and the media resumption card on Android, plus the fixes from the device checks and the gate (APK plugin check, failure-path tests).

Show all changes

Added

  • Radio → Browse stations: find internet radio stations in the Radio Browser directory (radio-browser.info) by country (each device remembers its pick), with language and genre pills. Tap to play; ♥ keeps a station in your stations. The server fetches the list and caches the station logos. Shows "Directory unavailable" when offline. There's no default country: the first visit asks for one and each device remembers it; Admin → Server can turn the directory off or set a default (D-74). Migration 0024_radio_directory (#58).
  • Android app: videos can be downloaded like songs (⋯ Download, album/playlist downloads, Download Quality, room check, Wi-Fi rule) and play offline in the native player; Music Only on a downloaded video plays the same file without the picture; their subtitles are kept with them (D-55, #140).
  • The video control bar's Picture in picture shows its state ("Exit picture in picture"); the P key toggles it; the window closes with the video view (Music Only, ✕) or for a song, and follows the next video (#78).
  • Android: native picture-in-picture for videos: leaving the app while a video plays opens it (auto-enter on Android 12+), and so does a new button in the video view; previous, play/pause and next; the video's aspect ratio. Music Only is unaffected (#78).
  • Android: low-memory handling (I-75): when Android is short of memory, the app releases the artwork cache, the WebView's memory cache, idle connections, other tracks' spectra and sprites, and (on critical levels) keeps a shorter player buffer and reads ahead only the current song for 10 minutes. Playback and the queue are never touched (#53).

Changed

  • Android: debug builds install as a separate app (io.aura.player.debug, "Aura (debug)") next to the real Aura; the release stays io.aura.player (D-75).
  • Android build: the APK build and release:verify fail when a native plugin class is missing from the APK; release builds start from clean Gradle outputs (#179).
  • Screenshot tests run inside Playwright's official Docker image pinned to our version, so the baselines are the same on every machine (#82).
  • Simpler track menu (right-click and ⋯): Add to queue · Playlist ▸ · Album · Info. Add to queue adds to the end and its toast offers Play next; Copy link, Download / Remove download, Remove from this playlist, Rate, Artist, Metadata and (web/desktop) Sleep timer left the menu; the Android app keeps Sleep timer in its ⋯ (#192).
  • Info dialog with tabs: Metadata first (the editor for admins, read-only for everyone else), with your rating and View artist, then Details (format, bitrate, size, plays); a link button in its header copies the song's link (the share sheet on Android). New GET /tracks/:id/tags for signed-in users (#192).
  • Web queue rows on computers (the floating queue and the queue page): the × is always at the far right; the ♥ (just left of it) and the drag grip (left of the cover) show on hover or keyboard focus and take no space otherwise (#189).
  • Videos: ← / → jump 10 s (songs keep 5 s) and show a badge on that side ("10 seconds", adding up on repeated presses), also announced to screen readers (#191).
  • The artist under the playing title links to the artist's page in the music view's mini player, the phone mini player and the Android app's play area and video controls (#193).
  • The web video mini player's progress line shows only with its other controls: on hover, keyboard focus or after a tap (#184).
  • Admin → Cache no longer repeats the This device song cache; it lives in Settings → Playback only (#185).
  • Admin → Stats → Health: the checks are compact tiles, two per row (one on phones), with a gap after the status icon (#190).

Fixed

  • Android: radio station logos now load in Browse stations and on Now Playing, and video seek previews on http servers; the server accepts ?token= on radio logos; Now Playing shows the placeholder instead of a broken image when artwork fails to load (#171).
  • Android: with shuffle on, every song in the queue now plays once before autoplay; Media3's random order could start mid-way, so some songs never played and autoplay came early (#170).
  • High contrast theme: the knob of a switched-on toggle is black on the yellow, so it stands out (it was white, 1.4:1). Other themes are unchanged (#147).
  • Autoplay no longer suggests songs you just removed from the queue (swiped away, deleted or cleared), also with the screen off on Android. Emptying Up Next by hand near the end of a song no longer refills it straight away; it waits for the Undo time. Undo after removing a queue item puts it back in place without duplicating a song (#151).
  • Android: the player no longer opens the song after the next one ahead of Read Ahead; an upcoming item buffers only 15 s and songs load in smaller steps, so each song is fetched once (B-58, #46).
  • Android: the media resumption card works after the app was killed; the playback service is now a MediaLibraryService, so SystemUI's resumption check succeeds (#124).
  • A library drive unmounted in the middle of a full scan no longer removes the tracks the scan hadn't reached yet (#130).
  • A backup that runs out of disk space now fails cleanly instead of hanging and blocking every later backup until a restart (#130).
  • A failed backup whose result can't be saved (database full too) no longer causes an unhandled rejection (#130).
  • High contrast theme: text on the yellow accent (Sign in and other primary buttons, empty-state actions, the avatar letter, the "New" badge, Up Next's "Play now") is black instead of white (1.43:1 → 14.7:1); other themes unchanged (#136).
  • The Info dialog's Plays row shows the full count ("1,234", not "1k") (#137).
  • Android: autoplay now continues after a shuffled queue has played every item; the autoplay items play next instead of at random places in the shuffle order (#125).
  • Subtitle files are served only when they are regular .srt/.vtt files up to 4 MB; a FIFO or a huge file no longer hangs or bloats the request (#143).
  • The 1.2 apps (web, desktop, Android) on a 1.1.0 server hide what the older server lacks instead of showing errors: Favorites → Albums and the album ♥, track Info, Copy link / Share, the instant search dropdown, Send diagnostics, Sign out other sessions, Forgot password?, and Admin → Backups, Server, Health and devices' caches (#144).
  • Video seek previews show in Chrome and Brave again: sprites, video thumbnails and resized artwork over 32 KiB were saved as WebP files with a broken header; sprites are made again (#183).
  • Video thumbnails and resized artwork that earlier versions (1.1.0 too) saved broken are repaired or made again in the background after the upgrade, with new image URLs so browsers drop the broken cached copies (#188).

0.12.0-alpha.1

2026-10-11Pre-release

First pre-release of 1.2.0, tagged on dev (internal; the owner's server stays on 1.1.0). New: the lyrics view, offline downloads (web, desktop, Android), native background autoplay, full-text and instant search, the selection bar with drag to playlists, seek and hover previews, loading skeletons and cover colours, a first-run guide, smart shuffle, swipe to remove in the queue, thin playing bars, every device's song cache in Admin, scheduled backups, a recovery code and Forgot password?, and Admin → Server settings; plus security fixes for symlinked lyrics files and folder covers. The API (/api/v1) stays compatible with 1.1.0 clients. Database migrations 0014–0017 and 0020–0023 run on the first start (a backup is taken first). Known: a 1.2 app on a 1.1.0 server shows errors on the new features (Favorites → Albums, Info, instant search, …); fixed for the next pre-release (#144).

Show all changes

Added

  • Loading skeletons: a page that takes a moment to load (Home, Music / All Tracks / Videos, Recent, Favorites, an album, artist or playlist, search results) shows grey shapes of its cards, rows or header in its place meanwhile, instead of the previous page under the progress bar; a quick load swaps the pages as before. They shimmer softly, not with reduced motion (U6).
  • Cover colours: while a cover loads, its main colour shows in its place (cards, rows, page headers, the player). The server works out each cover's colour once with ffmpeg, the first time the picture is asked for, and in a slow background pass over the covers that don't have one yet (no rescan); the API gives it as color (#rrggbb) on tracks, albums, artists and playlists, once known. Migration 0022_artwork_color (artwork.color) (U6).
  • Now Playing takes the cover's colour: the music Now Playing view and the phones' Now Playing sheet get a subtle tint of the playing song's cover over the background, and their seek bar (on a computer, the player bar's while the view is open) a shade of it that stands out in every theme; the accent stays red everywhere else, and the high-contrast theme has no tint (I-55).
  • Every device's song cache in Admin → Cache: under This device, Devices lists the song cache each device last reported, of every user: its icon, name (and owner, for other users' devices), "Last seen 2 hours ago" and "182 MB of 2 GB" with a bar. The web, the desktop app and the Android app send it when it changes (checked every few minutes, not per song). Server: the device.cache WebSocket message, admin GET /api/v1/devices/caches, migration 0021_device_cache (I-92).
  • Selection bar: Remove on playlist pages (U8).
  • Selection bar (desktop): with tracks selected, a bar offers Play next and Play last (U8).
  • Selection bar: Playlist opens the playlist picker (your playlists, then New playlist…), the same as the menus' Playlist ▸ (U8).
  • New playlist from a selection: New playlist… in the bar's picker or the selection's menu says "New playlist from these 12 tracks" and creates the playlist with them, in the order they're shown (I-64).
  • Selection bar on phones and in the Android app: fixed just above the player and the bottom bar, the count and icons only, 44px buttons. On touch screens, Select in a row's long-press menu starts a selection; taps then select or deselect rows (U8).
  • Drag to playlists (desktop): drag a track, or the selected tracks, onto a playlist in the sidebar to add them; the playlist lights up while you're over it. Dragging to reorder a playlist or the queue works as before (I-63).
  • Offline downloads (web with the installed app or https, the desktop app, the Android app): download an album or a playlist with the ↓ button next to its ♥, or a song or video with Download in its ⋯ menu (Remove download there and on the button removes it). Favorites → Downloads (a new tab after Albums, D-25) lists each download with its progress, Play and Remove, every downloaded track, how much room they take and what's left on the device, and Pause / Resume (Resume also retries failed ones) and Remove all. Downloads play offline with their artwork, lyrics and playing bars, and the Song Cache never removes them. Settings → Playback → Download Quality (this device): Original by default, or High / Normal (a song the device can't play as it is comes at High); downloads wait for Wi-Fi unless Download on Mobile Data is on (D-22). Before a download starts the app checks the room left and says when there isn't enough; a device that fills up pauses the downloads with a message. Downloads belong to your account on that server. The Android app downloads songs (videos play from the server there for now, D-55). No server change (P-DOWNLOADS).
  • Starting offline keeps your session: the Android app opened without a connection to the server now shows where you were, your queue and Now Playing, on Favorites → Downloads, with the "Offline" / "Reconnecting…" bar until the server answers again, instead of the Connect page. The installed web app and https sites do the same once this browser has downloads (the offline page otherwise, as before) (I-97, D-57).
  • High-contrast theme (Settings → General → Theme): black, white and yellow, AAA text contrast, strong borders and focus rings (I-78).
  • Send diagnostics (Settings → About): sends the app's recent log to the admins of the server, to look into a problem. The web page, the desktop app and the Android app each keep their last few hundred log lines in memory (failed requests with their request ids, errors, player events such as each Music Only tap and, in the apps, the native player's events); nothing secret is kept (passwords, tokens, cookies are replaced by [redacted]). Admins find the bundles under Admin → Stats → Diagnostics and download one as a JSON file that also holds the server's log lines from the minutes before it was sent. 10 per user an hour (I-13).
  • Server: log files with rotation: the log also goes to DATA_DIR/logs/aura-<date>.log (JSON lines; a new file every day and at 10 MB; kept 14 days and 200 MB in all; LOG_FILE, LOG_FILE_MAX_MB, LOG_KEEP_DAYS, LOG_MAX_TOTAL_MB). The first line says what the server runs with; sign-ins and sign-outs, WebSocket connections, slow requests (over 2 s), rate limits and failed sign-ins are logged too. aura logs prints them (-n, --level, --request <id>, --since 2h, --json); admins can read them over GET /api/v1/logs. See docs/ops/logs.md (I-13).
  • Android app: Autoplay keeps going with the screen off. When the queue's last item plays while the app is in the background (screen off, another app in front), the app's player now asks the server for similar items itself, so the music goes on even after Android has put the app's page to sleep (it used to stop at the end of the queue until the app was opened). Only the device that is playing does this (a phone another device took over from never fetches or starts anything), with the same streaming quality and Music Only setting as the app; offline, it tries again and goes on when the network is back (within a minute of the end). Opening the app shows the added items in Up Next as autoplay items (I-88, B-16, D-8).
  • Read Ahead (Settings → Playback): how many songs after the current one are kept whole on this device, so they play through a network drop: Next song (the default, as before), 3 songs or 5 songs. More than the next song only on Wi-Fi or another unmetered connection (mobile data, or a phone whose browser doesn't say, keeps the next song only), and the songs ahead never take more than half the Song Cache (the current and next song always). With shuffle, the songs read ahead are the ones that play next. Their playing bars are kept with them. Web, desktop and Android apps (I-90).
